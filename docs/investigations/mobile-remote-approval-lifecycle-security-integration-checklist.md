# 모바일 원격 승인 — Heartbeat 통합 교차검증 체크리스트

본 문서는 **Independent Security & Failure Reviewer**로서 다음 단계의 Heartbeat 및 Risk Guard 백엔드 통합 구현에 대비하여 수립한 **보안 검증 체크리스트**입니다.
---

## 1. CRITICAL 검증: Heartbeat Crash 후 Retry 구출 정책

하트비트가 승인을 소비(`consume`)한 직후 크래시가 났을 때, 재기동된 복구 런(Run 2)이 추가 승인 요구 없이 작업을 수행할 수 있도록 지원하면서도 비인가 권한 재사용을 차단하기 위한 검증 사양입니다.

### [체크리스트 및 판정 기준]
- [ ] **동일 Task & Fingerprint 검증**:
  - 재시도 런(Run 2)이 계산한 현재 시점의 `taskFingerprint`가 기존 승인에 기록된 `task_fingerprint`와 정확히 일치하는지 비교하는가? (이슈 설명 등이 바뀌어 작업 성격이 변조된 경우 재시도라도 거부되어야 함)
- [ ] **동일 Agent & Company 컨텍스트 검증**:
  - `approvals.companyId` 및 `approvals.requestedByAgentId`가 재시도 런의 메타데이터와 완전히 일치하는지 확인하는가?
- [ ] **가계도 추적 (Transitive Retry Path Verification)**:
  - 단순히 `retryOfRunId` 단일 뎁스만 비교하지 않고, `heartbeat_runs` 테이블을 재귀적으로 거슬러 올라가(Parent-child Chain) 최초 승인을 소모한 원본 `consumedByRunId`에 정상 도달하는지 검증하는가?
- [ ] **상태 위조 및 우회 방지**:
  - 스케줄러(Coordinator) 외의 악성 액터/에이전트가 임의로 `retryOfRunId`를 실패한 타인의 런 ID로 조작하여 `consumeApproval`을 우회 신청할 수 없는 구조인가? (임의 API를 통한 `retryOfRunId` 변조가 DB 제약 조건 및 인증 세션으로 보호되는지 확인)
- [ ] **중복 실행 방지 (Double Execution Guard)**:
  - 이전 런이 크래시 전에 이미 부분적으로 작업을 수행하여 결과물(Work Product)을 생성한 상태인지 감지하여, 재시도 시 중복 API 호출이나 리소스 낭비가 발생하지 않도록 방지책이 설계되어 있는가?

## 2. HIGH 검증: 트랜잭션 경계와 외부 Side-effect 불일치 통제

데이터베이스 트랜잭션의 커밋 여부와 비동기/외부 부작용(Side-effect) 발송이 어긋나는 불일치 문제를 해결하기 위한 경계 정의 사양입니다.

```
[트랜잭션 불일치 실패 시나리오]
┌───────────────────────────────┐
│ resolveApproval (DB Update)   │ ──> [성공]
└───────────────────────────────┘
                │
                ▼
┌───────────────────────────────┐
│ heartbeat.wakeup (외부 호출)   │ ──> [성공] (에이전트 즉시 가동 시작)
└───────────────────────────────┘
                │
                ▼
┌───────────────────────────────┐
│ DB Commit (커밋 실패 / 롤백)  │ ──> [실패] (승인 상태는 DB에서 여전히 Pending)
└───────────────────────────────┘
==> 결과: DB는 미승인 상태인데 에이전트는 승인된 줄 알고 작업을 이미 실행해버리는 보안 사고 발생!
```

### [체크리스트 및 판정 기준]
- [ ] **트랜잭션 격리 (Post-Commit Hook)**:
  - `heartbeat.wakeup()`, `logActivity()`, 푸시 알림 발송 등 데이터베이스 바깥 세상에 부작용을 일으키는 호출들이 DB 트랜잭션 커밋이 **완전히 완료(Successful Commit)**된 직후 호출되도록 보장하는가?
  - `db.transaction(...)` 블록 내부가 아닌, 프로미스 체인의 `.then()` 혹은 트랜잭션 종료 이후 블록에 해당 트리거들이 위치하는지 검증한다.
- [ ] **Outbox 패턴 지양 및 단순화**:
  - 시스템의 복잡도를 낮추기 위해 별도의 메시지 큐 테이블을 만드는 과도한 아키텍처 대신, 커밋 후 비동기 호출 방식으로 가볍게 구현하여 Stability First 원칙을 지켰는가?

## 3. Migration 순서 및 배포 호환성 검증 (Migration Sequence)

스키마 변경 파일(`0219`, `0220`)과 서버 애플리케이션 코드 배포 간의 동적 호환성을 검증합니다.

### [상태 비교 검증 결과]

| 배포 시나리오 | 런타임 결과 및 안전성 여부 | 판정 근거 |
| :--- | :---: | :--- |
| **코드 배포 후 마이그레이션 실행**<br>(Code $\rightarrow$ DB Migration) | ❌ **CRITICAL FAIL** (배포 즉시 마비) | 서버 기동 및 하트비트 루프 구동 시, 존재하지 않는 `expires_at`, `task_fingerprint` 등의 컬럼을 SQL 쿼리로 참조하여 즉시 런타임 SQL Syntax Error가 발생합니다. |
| **마이그레이션 후 코드 배포**<br>(DB Migration $\rightarrow$ Code) |   **PASS (Safe Staged)** | 마이그레이션이 먼저 적용되어 컬럼이 생성(기본값 NULL)되면, 구버전 코드는 해당 컬럼을 참조하지 않으므로 문제없이 작동합니다. 이후 신버전 코드가 배포되면 비로소 신규 컬럼을 정상 활용하기 시작하므로 배포 다운타임이 없습니다. |

- **최종 검증 규칙**: 검증 파이프라인에서 마이그레이션이 애플리케이션 빌드/배포보다 선행하여 격리 적용되도록 배포 순서 스크립트가 강제되어야 합니다.

## 4. 필수 테스트 케이스 검증 요구조건 (Test Suite Prerequisites)

최종 릴리즈 전에 아래 9가지 엣지 케이스 시나리오가 테스트 스위트(`server/src/__tests__/*`)에 반드시 명문화되어 정상 빌드되는지 확인합니다:

1. **`CONC-01`**: 거의 동시에 들어온 중복 승인 요청 중 단 1개만 통과하고 나머지는 409 Conflict 처리되는가?
2. **`CRASH-02`**: 승인을 소비한 직후 하트비트가 중단되었을 때, 신규 복구 런이 추가 승인 요구 없이 무사히 기동되는가?
3. **`fingerprint mismatch`**: 승인 완료 후 작업 명세 텍스트나 이슈 설명이 변경되었을 때, 재개 시점에 승인이 자동 기각 처리되는가?
4. **`expired approval`**: 15분이 경과한 승인 요청에 대한 승인 시도 시 정확히 410 Gone 오류가 발생하는가?
5. **`same-run retry`**: 동일 런 내부에서의 연속적인 멱등 재시도는 추가 소모 기록 없이 무사통과되는가?
6. **`cross-run rejection`**: 관계없는 다른 런이 기존 승인을 사용하려고 시도할 때 즉시 차단되는가?
7. **`transaction rollback`**: 승인 처리 도중 강제 예외 발생 시 DB가 완전 롤백되어 Pending 상태로 복구되는가?
8. **`restart recovery`**: 트랜잭션 커밋 직후 서버 데몬 재시작 시, 메모리 유실과 상관없이 기동 틱이 승인 상태를 DB에서 안전하게 읽어와 실행을 지속하는가?
9. **`existing Risk Guard regression`**: 기존의 모델 변경 권한 가드나 일반 승인 흐름들이 신규 컬럼 추가 이후에도 아무 부작용 없이 호환 작동하는가?

---

## 5. UNKNOWN TTL 정책 분리 검토

- `UNKNOWN` 위험 등급의 TTL을 HIGH와 동일한 15분으로 유지할지, 혹은 더 엄격한 5분 만료 정책을 도입할지는 에이전트 운용 아키텍처 결정 사항이므로, Claude 통합안 코드 병합과 섞이지 않도록 **별도 보안 정책 마일스톤**으로 분리 관리함을 기본 원칙으로 확인합니다.
